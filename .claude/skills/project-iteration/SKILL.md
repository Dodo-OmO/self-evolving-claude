# 项目迭代主流程

这是把整套工程系统串起来的"主控流程"——其它 agent / skill / hook 都是它在各阶段调用的下游工具。本骨架是通用模板，按你的项目实际裁剪（删掉用不到的步骤、替换成你的目录与命令）。

## 步骤 1：懂项目

开工先读项目背景文档 / 架构文档，进入"懂这个项目当下全貌"的状态，再动方案。不带着旧印象拍脑门。

## 步骤 2：方案对齐

- 从用户"想要的效果"出发**独立审视**，不照单全收——用户不一定懂技术实现，建议不一定对。
- 拿不准时**多查同类成功案例**取启示，不拍脑门。
- **大改动**（≥2 处行为协议 / 改架构 / 加新组成 / 重构 ≥100 行）：① v1 方案**先派 `devil-advocate` 内审** → 消化 Critical + Required 进 v2；② 给用户 **3 个候选方案**（各注核心做法 / 代价 / 适合场景）而非只抛一个；③ v2 首次汇报**把"改动前后的 token 增减估算"明示给用户**。小改动跳过。
- 出方案两自检：① **已有功能不另起炉灶**（grep 同名/近义函数，能复用就复用）② **token 优化**。
- **集中问清闸**：所有模糊点 / 设计分叉 / 取舍**一次性问完**（自主连续执行模式下，这是唯一的前置停顿——开工后不再回头问本可一次问清的事）。

## 步骤 3：建任务文档

- 复制任务文档模板，填：任务背景 / 当前基线 / 对齐后方案 / Not-Doing 清单 / 风险识别 / **实操详细计划**。
- 「实操详细计划」要详细到**无脑可执行**：每步动哪个文件:行 + 可验证的验收标准 + 失败回滚方式 + 跨步依赖。这段是执行阶段的唯一抓手。

## 步骤 4：执行循环

`读文档 → 执行 → 验证 → 立刻记文档 → 推下一步`

- **并行判断**：≥2 个互不冲突的独立代码块 → 走 `parallel-exec`；否则 solo。**工程系统文件（.md/hook/skill/CLAUDE.md）一律 solo**。
- **每步验证 = 派 `code-reviewer` 两阶段审**；FAIL → 派 `bug-fixer` 修 → 重审，循环到 PASS。
- **commit 锚定"逻辑完整 + 已验证"**，不按编辑次数。
- 执行中保持警惕：发现方案不对，**先验证找证据再改**，不硬按错的方案往下做。

## 步骤 5：验收

汇报成果 + 把需要用户**真机实测**的项拉一份清单，一次性交用户测。测出问题回步骤 2/3/4 循环（继续维护同一个任务文档，不另起新文档）。

## 步骤 6：收尾

- 任务文档「结果」填三态（✅成功 / ❌失败 / 🟡放弃，严格区分失败和放弃）。
- 按需：版本备份 + **回写项目背景文档**——只写"当前最正确的状态"，不写变更历史 / 不写"为什么从 X 改到 Y"（那是 git log 的事）。

> 另可定期做**项目体检**：跳出单次迭代，对整个代码库 + 工程系统做全局扫描，找过度工程、prompt 冗余、孤儿代码、新老打架的残留——发现的问题进迭代队列。

## 跨 session 接力

用户说"交给下个 session 接力"时：写一段**可直接复制**的交接文字——① 已建任务文档的路径（提醒下个 session 续用、别开新文档）② 文档里没写但你已调查到 / 用户口头告诉你的关键信息 ③ 确保无缝接力的其它上下文。发完交接文字就**停**，不再继续执行。

## 与进化系统的衔接（Steering Loop）

```
用户给反馈
  → detect-feedback-signal hook 提示
  → 派 feedback-observer 写入 .claude/feedback/<类目>.md（泛化成可复用规则，按归并键去重）
  → ……累积到同类 ≥3 次……
  → 新 session check-evolution hook 提示
  → 派 evolution-runner 识别毕业候选、给升级建议
  → 用户逐条确认
  → 毕业进 CLAUDE.md / 对应 Skill 的硬规则
  → 已毕业条目移到 EVOLUTION.md（保留追溯）
```

这条闭环让工程系统**随用随长**：今天的反馈是明天的硬规则。
